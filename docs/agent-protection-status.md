# Кабинет агента: защита и удобство

Ветка `codex/agent-protection`. Изменения подготовлены к проверке в PR, не опубликованы. `main`, production-данные, `.openai/hosting.json`, DNS и переменные окружения не менялись.

## Реализовано

1. Оба обработчика заявок отклоняют собственный email/телефон агента (422, `SELF_REFERRAL`). Телефоны с `+7`, `8`, пробелами и скобками сравниваются после нормализации. Пустые контакты не считаются совпадением. Проверка выполняется до записи заявки и загрузки файлов.
2. Обе публичные формы имеют скрытое антиспам-поле. Заполненное поле отклоняется до чтения/записи бизнес-данных и загрузки файлов; перед этим обновляется только служебный IP-счётчик. Это дополнительный фильтр, **не замена IP-лимиту или капче**.
3. Все четыре API подтверждения/входа используют общую функцию сравнения хэшей без остановки на первом отличающемся символе. Удалены копии этой функции из авторизации компании и администратора. Формат паролей и токенов сохранён.
4. Неисправные ссылки открывают понятную страницу с входом по email. Добавлены error boundaries с повторной попыткой. Для ошибки в layout агента предусмотрена также родительская граница.
5. Префиксы доменной маршрутизации перечислены явно. Тест обходит страницы `app/` и падает при новом неклассифицированном разделе.
6. [Предложение по единой личности агента](agent-identity-review.md) описывает текущие места группировки и вариант постепенного перехода. Исторические участия не объединялись и не удалялись.
7. Голосовые заявки используют существующее атомарное резервирование кредитов компании. Максимальный резерв — 120 кредитов; после ответа списывается фактический расход, остаток возвращается. Ошибка провайдера возвращает резерв. Результат остаётся черновиком, автоматической отправки заявки нет.
8. В кабинете показан срок **конкретной текущей ссылки**. Детали свёрнуты; рядом есть способ получить новую ссылку. Долгоживущий вход по токену сохранён.
9. Агент получает email при смене проверки/продажи, одобрении вознаграждения и отметке перевода. Массовая отметка выплат собирает одно письмо на email, даже при нескольких программах одной компании. Повторное сохранение без смены статуса не создаёт новое уведомление. Письма не содержат телефонов клиентов или долгоживущих токенов; вход — через email и выбор компании.
10. Страницы/ответы кабинета агента не кешируются. Добавлены `Referrer-Policy: no-referrer` и `X-Robots-Tag: noindex, nofollow` для приватных агентских маршрутов.

## Лимиты: реализованы после разрешения владельца

- Два публичных обработчика делят один бюджет: 30 запросов с IP за 15 минут. Смена формы, токена или `X-Forwarded-For` не обходит лимит. Считаются также ошибочные запросы и honeypot.
- Подтверждение контакта: максимум 5 проверок кода за 15 минут на человека внутри компании и канал. Форматные ошибки и истёкшие коды также расходуют попытку. Пятый правильный код принимается; после пяти неверных проверок действует блокировка до конца окна.
- Повторная выдача кода и новая ссылка входа не сбрасывают попытки. Выдача ограничена отдельно: 5 кодов за 15 минут. Весь обработчик дополнительно ограничен 60 запросами с IP за 15 минут.
- При выдаче нового кода прежние неиспользованные коды этого участия и канала становятся недействительными. Правильный код можно использовать только один раз, в том числе при одновременных запросах. Проверка и отметка подтверждения выполняются атомарно и сверяют актуальный контакт.
- Ответ 429 содержит `Retry-After` и `retryAfterSeconds`. Интерфейс показывает обратный отсчёт, временно отключает отправку и подтверждение, затем позволяет запросить новый код. Добавлен казахский перевод.
- Ошибка доступа к счётчикам возвращает 503 с повтором через минуту: защита не отключается молча, бизнес-записи и отправка писем не выполняются.

### Таблица и миграция

`0030_request_rate_limits.sql` создаёт только `request_rate_limits` и индекс `idx_request_rate_limits_reset_at`:

| Поле | Назначение |
| --- | --- |
| `key_hash` | SHA-256 от назначения счётчика и его ключа, первичный ключ |
| `hits` | Число запросов; после блокировки ограничено значением лимит + 1 |
| `reset_at` | Конец 15-минутного окна, Unix milliseconds |

Открытые IP, email, номера и токены в новую таблицу не пишутся. Хэш IP — не гарантия анонимности. При поступлении запросов удаляются до 100 истёкших технических счётчиков за операцию; при отсутствии трафика они могут оставаться до следующего запроса. Это не планировщик с гарантированным сроком физического удаления. Блокированные запросы не продлевают окно.

Доверяем только `CF-Connecting-IP` от Cloudflare, не пользовательскому `X-Forwarded-For`. Эквивалентные IPv6-адреса нормализуются. При отсутствии корректного заголовка запросы делят ограниченный запасной счётчик: на другом хостинге это может ограничить несколько пользователей вместе. DNS, прокси и окружение не менялись. Основание: [заголовки Cloudflare](https://developers.cloudflare.com/fundamentals/reference/http-headers/), [атомарные D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch).

В старом журнале отсутствует запись 0029, а последний snapshot — 0026. Чтобы не повторить изменения прежних SQL, Drizzle сгенерировал дельту между актуальной схемой до/после добавления счётчиков во временной папке. Добавлены только SQL 0030, актуальный snapshot и новая запись журнала. Прежние миграции и записи журнала не переписывались. Повторный `pnpm db:generate` сообщает, что новых изменений схемы нет. Миграция проверена на заполненной временной базе и D1-эмуляторе; **в production пока не применена**.

## Проверки и ограничения

- `pnpm lint`: завершён, 0 ошибок; 7 прежних предупреждений об использовании `<img>`.
- `pnpm test`: сборка успешна, 77 тестов прошли, 0 ошибок.
- `tests/mission-workflow.test.mjs` и `tests/agent-account-access.test.mjs` теперь вызывают реальные обработчики и запросы к временной SQLite, а не ищут строки в исходниках.
- Проверены саморефералы, honeypot, дубли, разные компании, сроки ссылок, блокировка доступа, существующий лимит входа агента, отправка файлов и заявок, ошибки и конкуренция голосовых запросов, уведомления.
- Новые тесты вызывают реальные API: общий IP-бюджет двух форм, отсутствие обхода через заголовок/перевыпуск ссылки/кода, 5 попыток, истечение окна, независимость компаний и каналов, ошибка таблицы без бизнес-записей, конкурентные запросы и одноразовое подтверждение. Отдельный DOM-тест проверяет обратный отсчёт и повторную выдачу кода.
- Миграция оставляет все ранее существующие записи временной SQLite неизменными. Реальный D1-эмулятор Miniflare дополнительно проверяет миграцию, конкурентный UPSERT и атомарное потребление кода через `changes()`.
- Собранный Worker проверяется на HTTP-ответах: недействительные ссылки возвращают 404 с текстом восстановления. UI-компоненты проверены через HTML/DOM без использования реальных персональных данных.
- Внешние отправки писем, Gemini и R2 заменены тестовыми адаптерами. Реальные письма и заявки не отправлялись. Это не проверка доставки в production.
- Email-уведомления используют текущий канал Resend. Отправка ограничена пятью секундами и не отменяет сохранённый статус при сбое. Долговременной очереди/повторной доставки пока нет; гарантированная доставка потребует отдельной работы. WhatsApp не подключался.
- Для новых SQL-тестов требуется Node ≥22.16; это отражено в `package.json`. CI использует актуальную Node 22. Версии зависимостей не менялись.
- Дополнительная проверка `tsc --noEmit` обнаружила существующую в `main` ошибку типа `plannedAt` в `app/dashboard/crm/crm-workspace.tsx:118`. В рамках агентского PR этот посторонний участок не менялся.

Следующий шаг: отдельно разрешить публичное обновление, затем применить новую миграцию перед включением новой версии обработчиков. Откат только кода совместим с оставленной таблицей счётчиков. Предложение по единой личности требует отдельного согласования и не входит в миграцию счётчиков.
