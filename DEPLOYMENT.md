# Развёртывание RiseStaff

Эта инструкция описывает публикацию текущего приложения в существующий Sites-проект RiseStaff.

## 1. Доступы

У участника должны быть:

1. доступ к репозиторию `risestaff11-eng/RelayMVP`;
2. роль Editor или Owner в Sites-проекте RiseStaff;
3. доступ к production-переменным окружения, если их требуется изменить;
4. доступ к DNS-зоне `risestaff.kz` только при изменении доменов.

Один доступ к GitHub не даёт права менять production, базу D1, R2 или DNS. Это намеренное разделение прав.

## 2. Привязки платформы

Файл `.openai/hosting.json` уже связывает исходники с существующим Sites-проектом и объявляет bindings:

| Binding | Тип | Назначение |
| --- | --- | --- |
| `DB` | D1 | пользователи, компании, программы, результаты, выплаты и анонимные marketing events |
| `FILES` | R2 | аватары, вложения и материалы |

Не меняйте `project_id`, имена bindings или домены без согласования: это может создать отдельное хранилище или нарушить маршрутизацию production.

## 3. Переменные окружения

Production-значения задаются в Sites, а не в `.env` и не в GitHub.

| Переменная | Обязательность | Назначение |
| --- | --- | --- |
| `ADMIN_SECRET` | для системной админки | подпись защищённой admin-сессии; длинная случайная строка |
| `GEMINI_API_KEY` | для AI-функций | ключ Gemini API |
| `AI_PROVIDER` | опционально | значение `gemini` |
| `GEMINI_MODEL` | опционально | по умолчанию используется модель из `lib/ai.ts` |
| `RESEND_API_KEY` | для автоматической активации компании | отправка кодов подтверждения компаниям и magic-link писем агентам |
| `MAGIC_FROM_EMAIL` | для автоматической активации компании | подтверждённый адрес отправителя Resend |
| `WHATSAPP_VERIFY_WEBHOOK_URL` | опционально | webhook отправки WhatsApp-кодов |
| `WHATSAPP_VERIFY_WEBHOOK_TOKEN` | опционально | bearer token для webhook |

Никогда не добавляйте реальные значения этих переменных в коммиты, PR, issue или логи CI.

## 4. Проверка перед публикацией

```bash
corepack enable
pnpm install --frozen-lockfile
pnpm lint
pnpm test
```

Если менялась схема D1:

```bash
pnpm db:generate
git diff -- drizzle db/schema.ts
```

Проверьте, что миграция только добавляет или намеренно изменяет нужные таблицы и не удаляет production-данные.

## 5. Публикация через Sites

1. Откройте репозиторий в Codex с установленным плагином Sites.
2. Убедитесь, что `.openai/hosting.json` содержит существующий `project_id`.
3. Выполните проверки из раздела выше.
4. Закоммитьте и отправьте точное состояние исходников в GitHub.
5. Попросите Sites сохранить новую версию из текущего commit SHA и подготовленного build archive.
6. Опубликуйте сохранённую версию в production.
7. Дождитесь статуса `succeeded` и проверьте `https://risestaff.kz/`.

Sites применяет версионируемые миграции из `drizzle/` и сохраняет каждую публикацию как отдельную версию, что позволяет видеть, какой commit находится в production.

## 6. Проверка после публикации

- `https://risestaff.kz/` открывает лендинг;
- `https://company.risestaff.kz/` ведёт в кабинет компании;
- агентская ссылка открывается на `https://agents.risestaff.kz/`;
- `/robots.txt` и `/sitemap.xml` отвечают `200`;
- регистрация компании ведёт на правильный домен;
- D1 доступна и новая миграция применена;
- загрузка файлов работает через R2;
- секреты и персональные данные не появились в логах.

## 7. Откат

При проблеме не переписывайте историю GitHub и не удаляйте D1/R2. В Sites повторно разверните последнюю стабильную сохранённую версию, затем исправьте причину отдельным PR.
